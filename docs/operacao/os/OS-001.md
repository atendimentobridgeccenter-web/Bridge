## 1. Contexto (cérebro)
A função `public.set_admin_role(uuid)` (migrations 003 e 006) é `SECURITY DEFINER`, grava `role: admin` em `auth.users` e não confere quem chama. Nenhuma migration revoga o `EXECUTE`, e no Supabase funções do schema `public` nascem executáveis por `anon` e `authenticated`. Qualquer conta (aluno, professor) pode virar admin com um `POST /rest/v1/rpc/set_admin_role`. `is_admin()` também é `SECURITY DEFINER` sem `search_path`.

## 2. Escopo (cérebro)
**Faz:**
- Migration nova `030_lock_admin_role.sql` que:
  - remove `set_admin_role` (promover admin passa a ser só pelo SQL Editor, com o comando documentado no cabeçalho), **ou** mantém a função com `revoke execute from public, anon, authenticated` — o operador escolhe e justifica; preferência do cérebro: remover.
  - recria `is_admin()` com `set search_path = ''` sem mudar o comportamento.
- Cabeçalho da migration com SQL de conferência pós-aplicação.

**Não faz:**
- Não mexe em políticas de outras tabelas.
- Não altera usuários existentes (a revisão dos admins é ação do Everton).

## 3. Critérios de aceite (cérebro)
- [ ] Depois da migration, nenhum papel além de `postgres`/`service_role` consegue executar algo que promova usuário a admin.
- [ ] `is_admin()` continua retornando o mesmo resultado e tem `search_path` fixo.
- [ ] Nenhuma referência a `set_admin_role` no `src/` ou nas Edge Functions fica quebrada.
- [ ] Migration idempotente e com cabeçalho em pt-BR.
- [ ] typecheck, lint (0 erros) e build limpos.
