## 1. Contexto (cérebro)
A política `anyone_select_coupons` deixa qualquer visitante baixar a tabela `coupons` inteira: códigos ativos e inativos, valores, limites de uso. Quem achar um cupom de desconto alto usa e divulga. O único uso público é o `applyCoupon` do nó de depósito bancário no `QuizzRunner`, que só precisa saber se **um** código digitado é válido e quanto ele desconta.

## 2. Escopo (cérebro)
**Faz:**
- Migration `032_coupons_private.sql`:
  - `drop policy if exists "anyone_select_coupons"`;
  - criar `admin_select_coupons` (`for select to authenticated using (role = 'admin')`, mesmo padrão inline das outras políticas da 010);
  - criar `public.validate_coupon(p_code text) returns table (code text, discount_type text, discount_value numeric, applies_to text)` que devolve **uma linha** só se o código (comparado em maiúsculas, sem espaços) estiver ativo, não expirado e abaixo de `max_uses`; senão, zero linhas.
- Cabeçalho em pt-BR com motivo e conferência.

**Não faz:**
- Não muda o `QuizzRunner` (OS-007, OP-01).
- Não incrementa `uses_count` (registrar como achado se fizer sentido).
- Não mexe em cupons do Stripe nem no `sync-stripe-product`.

## 5. Relatório de entrega (operador)

**Migration criada:** `supabase/migrations/032_coupons_private.sql` (não aplicada — aplicação é Ação do Everton).

**O que a migration faz:**

1. **Cria `admin_select_coupons`** (nova — a `010_coupons_table.sql` nunca teve policy de SELECT para admin, só INSERT/UPDATE/DELETE). Vem **antes** do drop da policy pública, na mesma migration/transação, para nunca existir um instante sem nenhuma policy de SELECT na tabela.
2. **Remove `anyone_select_coupons`** (a policy pública da 010, que deixava qualquer visitante ler a tabela `coupons` inteira — códigos ativos e inativos, valores, limites de uso).
3. **Cria a RPC `public.validate_coupon(p_code text)`**, que devolve `code, discount_type, discount_value, applies_to` para um único código, ou zero linhas se ele não existir, estiver inativo, expirado ou tiver atingido `max_uses`.

**Design da RPC (mapeado contra os riscos do Gate 1):**
- `security definer`, `stable`, `set search_path = ''`, nomes totalmente qualificados (`public.coupons`) — evita sequestro de search_path.
- Entrada normalizada com `upper(trim(p_code))`, igual ao front (`QuizzRunner.tsx:809`, `trim().toUpperCase()`).
- Comparação por **igualdade** (`c.code = ...`), nunca `LIKE`/`ILIKE` — fecha a porta de enumerar códigos por tentativa/wildcard.
- `limit 1` e retorno vazio quando não há match — não revela se o código existe mas está inativo/expirado vs. nunca existiu (mesma resposta: zero linhas).
- `revoke all ... from public` + `grant execute` explícito só para `anon, authenticated` (as duas roles que o Supabase concede automaticamente por padrão em funções novas do schema `public` — sem o grant explícito, o revoke isolado não bastaria).

**Achados fora de escopo (registrados, não corrigidos aqui):**
- A RPC não incrementa `uses_count` — está explicitamente fora do escopo desta OS ("Não faz"). Quem decrementa o limite de uso continua sendo outro fluxo (fora do território desta entrega); se não existir hoje, fica como achado para uma OS futura.
- `QuizzRunner.tsx` ainda lê a tabela `coupons` diretamente — é a OS-007 (OP-01) que troca essa leitura pela chamada à RPC. Até a OS-007 ser entregue e a migration 032 ser aplicada em conjunto, o fluxo de cupom no quiz quebra (RLS vai bloquear o SELECT direto do anon). **Não aplicar a 032 antes de o front já estar chamando `validate_coupon`.**

**Checks executados (nenhum arquivo `.ts`/`.tsx` foi tocado nesta OS — só migration SQL):**
- `npm run typecheck` → 0 erros.
- `npm run lint` → 0 erros (14 warnings pré-existentes, nenhum em arquivo tocado por esta OS).
- `npm run build` → build limpo.
- Migration **não aplicada** (Proibido para o operador — Ação do Everton).
